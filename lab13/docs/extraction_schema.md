# Схема витягу та інструкція розмітки (ЛР13, результат 1) — версія 2

Основа — класи й об'єктні властивості онтології ЛР8 (`lab08_vocabulary.ttl`, простір імен
`http://www.semanticweb.org/energy-forecasting#`) і мітки/зв'язки графа ЛР9. Канонічні ідентифікатори сутностей
збігаються з `id` вузлів графа ЛР9 — це й є entity linking (результат 5).

## 0. Зв'язок зі схемою понять ЛР7

Концептуальна схема ЛР7 («Формалізація предметної області») має 8 базових сутностей і властивість `region`.
Типи витягу виведено з неї так:

| Поняття ЛР7 | Тип витягу | Примітка |
|---|---|---|
| Substation, властивість region | SUBSTATION, REGION | регіон — окремий тип, бо в тексті області названо прямо (у ЛР9 — вузли Region) |
| Consumer | CONSUMER | підкласи (побутовий / комерційний / промисловий) — атрибут, не тип |
| Meter | METER | |
| ForecastModel (статистична VAR / ML LSTM) | MODEL, METHOD | конкретна модель і клас методу розділено |
| Dispatcher | DISPATCHER | |
| WeatherCondition (температура, хмарність) | WEATHER_FACTOR | у текстах фігурують змінні, а не окремі дні погоди |
| Measurement, Forecast | — | у текстах майже не мають власних назв (дата + число), тому не витягуються |
| — | METRIC | нове поняття: метрики якості з бази знань (kb03), у ЛР7 їх немає |

Відношення відповідають об'єктним властивостям ЛР7/ЛР8: `connectedToSubstation` → CONNECTED_TO, `hasMeter` →
HAS_METER, `managedByDispatcher` (обернено) → MANAGES, `generatedByModel` + прогноз для підстанції → FORECASTS_FOR,
`upstreamOf` → FEEDS, `region` → LOCATED_IN, підкласи ForecastModel → INSTANCE_OF.

## 1. Типи сутностей (9)

| Тип | Що розмічаємо | Приклад (так) | Контрприклад (ні) | Канонічний ID |
|---|---|---|---|---|
| SUBSTATION | конкретна підстанція з номером | «підстанції №7», «№10 живить №4» | «магістральна підстанція» без номера; «Підстанція» як клас онтології | `Substation_7` |
| CONSUMER | конкретний споживач із номером | «споживача №3310», «Consumer_5019» | «промислові споживачі» (категорія) | `Consumer_3310` |
| METER | лічильник з ідентифікатором | «AMI-77410» | «трифазні лічильники» | `Meter_AMI77410` |
| MODEL | конкретна модель прогнозування з номером | «LSTM №2», «моделі LSTM: №1 …» | «моделі LSTM» без номера (це METHOD) | `ForecastModel_LSTM2` |
| DISPATCHER | диспетчер з номером | «диспетчер №3» | «провідний диспетчер» без номера | `Dispatcher_3` |
| REGION | область | «Львівська область», «у Закарпатській області», «Львівської та Волинської областей» | «у Львові» (місто), «закарпатські підстанції» (прикметник) | `Region_Lviv` |
| METHOD | клас методів прогнозування (закритий словник: ARIMA, SARIMA, VAR, LSTM, GRU) | «ARIMA», «типу VAR», «три моделі LSTM» | «LSTM» усередині назви моделі «LSTM №1»; «ансамблі», «бустинг» (поза словником) | `ARIMA` |
| METRIC | метрика якості прогнозу (MAE, RMSE, MAPE, sMAPE, WAPE, pinball loss) | «MAE», «sMAPE» | «похибка 7,5 %», «точність 81 %» (значення, а не метрика) | `MAPE` |
| WEATHER_FACTOR | погодна змінна (температура, хмарність, вологість, вітер, HDD, CDD) | «температура повітря», «хмарність — ясно», «HDD» | «похолодання», «мороз» (явища, не змінні) | `TEMPERATURE` |

## 2. Типи відношень (7)

| Відношення | Голова → хвіст | Приклад (так) | Контрприклад (ні) |
|---|---|---|---|
| FEEDS | SUBSTATION → SUBSTATION | «№1 живить підстанції №10, №2 і №7»; «живиться від підстанції №1» (обернено); «ланцюг №7 → №5 → №12» | «аварія на №1 зачіпає №4 на глибині 2» (опосередковано) |
| LOCATED_IN | SUBSTATION → REGION | «Підстанція №5 (Волинська область)»; «№9 у Закарпатській області» | регіон споживача без підстанції |
| MANAGES | DISPATCHER → SUBSTATION | «Відповідальний — диспетчер №4»; «Зона відповідальності: підстанції №1, №10» | «тимчасово події на №9 обробляє диспетчер №5» |
| CONNECTED_TO | CONSUMER → SUBSTATION | «споживач №5038, підключений до підстанції №1»; «комерційний №3310 (120 кВт) на №5» | «35 споживачів потрапляють під відключення» |
| HAS_METER | CONSUMER → METER | «AMI-77410 комерційного споживача №3310»; «Лічильники (2): AMI-81841, AMI-99231» | «лічильник замінено підмінним» без ID |
| FORECASTS_FOR | MODEL → SUBSTATION | «модель ARIMA №1 … прогнозує … для підстанцій №3 і №8»; «прогноз для підстанції №11 … згенеровано моделлю LSTM №2» | «диспетчер використовує прогноз моделі VAR №1» (без підстанції) |
| INSTANCE_OF | MODEL → METHOD | «Модель VAR №1 — статистична модель типу VAR»; «три моделі LSTM: №1, №2 і №3» | лише назва «LSTM №1» без окремого твердження про тип |

## 3. Інструкція розмітки

1. Розмічається **текст документа без YAML-заголовка**; офсети — у символах від початку цього тексту.
2. **Сутність** — один запис на (документ, тип, канонічний ID); `text` і `start` — перша згадка. Повторні згадки
   окремо не розмічаються.
3. **Відношення** — лише явно стверджене в тексті (без висновків за транзитивністю, без знань «з голови»). Один запис
   на (документ, тип, голова, хвіст); `evidence` — мінімальний дослівний фрагмент (до одного речення), що його
   стверджує; він мусить бути підрядком тексту.
4. Номер без слова «підстанція» (`№4`) розмічається як SUBSTATION, якщо з контексту речення/розділу зрозуміло, що
   мова про підстанції (ланцюг живлення, «ПС №»). Номер у переліку після «моделі LSTM:» — MODEL.
5. Чотиризначні номери після «споживач» / у переліку споживачів — CONSUMER; форма `Consumer_5019` теж CONSUMER.
6. Метод (METHOD) розмічається лише як окреме слово поза назвою моделі (`LSTM №1` → лише MODEL).
7. INSTANCE_OF — лише за окремого явного твердження про тип моделі («типу VAR», «моделі LSTM: №1…»).
8. MANAGES — лише постійне призначення («відповідальний», «зона відповідальності»); тимчасове обслуговування — ні.
9. FEEDS — лише пряме живлення: «живить», «живиться від», стрілки в ланцюгу живлення; «зачіпає на глибині N» — ні.
10. Підмет, названий у заголовку розділу (`## Підстанція №7`, `## Споживач №3310`, `## Модель VAR №1`), вважається
    названим і в реченнях цього розділу («Відповідальний — диспетчер №1» → MANAGES(Dispatcher_1, Substation_7)).
11. Значення (похибки, точність, кВт, дати) не є сутностями; адреси й персональні дані не розмічаються.

**Граничні випадки:** див. контрприклади в таблицях; рішення пілоту — `docs/pilot.md`.

## 4. JSON-схема виходу (обидва методи)

```json
{
  "doc_id": "kb12", "method": "rules|llm", "model": "spacy-3.8 rules v2 | qwen2.5:7b", "prompt_version": "extract_v2",
  "kind": "entity", "type": "SUBSTATION", "canonical": "Substation_7", "text": "№7", "start": 300, "end": 302,
  "confidence": 0.9
}
{
  "doc_id": "kb12", "method": "llm", "model": "qwen2.5:7b", "prompt_version": "extract_v2",
  "kind": "relation", "type": "FEEDS", "head": "Substation_1", "tail": "Substation_10",
  "evidence": "Магістральна підстанція №1 (Львівська область, 2500 кВт) живить підстанції №10, №2 і №7.",
  "start": 230, "end": 318, "evidence_verified": true, "attempt": 1, "confidence": 0.6
}
```

Відповідь LLM (метод Б) обмежено JSON-схемою Ollama `format` з переліками (`enum`) типів — закритий словник.

## 5. Правила нормалізації

| Тип | Правило | Приклад |
|---|---|---|
| SUBSTATION, DISPATCHER | номер без провідних нулів → `Substation_<n>`, `Dispatcher_<n>` | «ПС №07» → `Substation_7` |
| CONSUMER | 4 цифри → `Consumer_<nnnn>` | «№5038», «Consumer_5038» → `Consumer_5038` |
| METER | 5 цифр після AMI → `Meter_AMI<nnnnn>` | «AMI-77410» → `Meter_AMI77410` |
| MODEL | метод великими літерами + номер → `ForecastModel_<METHOD><n>` | «LSTM №2», «lstm-2» → `ForecastModel_LSTM2` |
| REGION | основа назви області (будь-який відмінок) → ID графа | «Закарпатській області» → `Region_Zakarpattia` |
| METHOD, METRIC, WEATHER_FACTOR | закритий словник, регістр нормалізується | «smape» → `sMAPE`; «температурою» → `TEMPERATURE` |

Реалізація — `src/schema.py::canonical()`; значення, що не нормалізуються, відкидаються валідатором.
